# 03 · 通知与推送设计

## 1. 事件与受众

| 事件 | 触发点 | 受众 | 通知文案（草案） |
|---|---|---|---|
| 新工单 | `process_inbound` 返回 `created=True` | 该组全体成员 | 「组内新工单 T#123：<主题>」 |
| 客户新来信 | `process_inbound`，`created=False` | ① 认领人；② **未认领时 → 该组全体** | 「T#123 有新来信」 |
| 改派 | `reassign_ticket()` 成功后 | **新组**全体成员（原组已失可见） | 「T#123 已改派到本组」 |
| 内部备注 | `add_note()` 后 | ① 被 @ 者；② 认领人 | 「张三在 T#123 中提到了你」 |

### 三条全局规则

1. **不通知动作发起人自己**（你回复完不该收到自己的通知）。
2. **同一个人不重复推**（组广播与认领人重合时只推一条）。
3. **`status="closed"` 的工单不推。**

### 用户确认的受众语义

> 未认领全推，认领之后只推给认领的人。

**已确认采用。** 与开发文档 §2.6「认领后只有认领人看到待回复」是同一套所有权模型，
用户不必学两套规则。

**已知运维后果（必须记录）**：认领人休假 / 离职 / 就是不看手机时，**该工单对全组静默**。
`assignee` 是 `SET_NULL`，用户被删会自动退回全组广播——「人不在系统里」有兜底，
**「人在但不看」没有**。用户明确选择不加超时推送（未勾选该事件）。
若将来被咬到，最小成本补丁是「管理员每日待回复摘要」。

## 2. 去重与聚合（不做就是噪音炸弹）

一次 IMAP 轮询（默认 60s）可能涌入几十封邮件。

- **同工单聚合**：60s 窗口内同一工单的多个事件 → 一条「T#123 收到 3 封新来信」
- **同组聚合**：同一组的多个新工单 → 一条「组内新增 3 个工单」
- **必须异步**：走 RQ 队列（`apps/mailboxes/tasks.py::dispatch` 已有"Redis 不可用则同步降级并告警"
  的机制），**不阻塞收信流水线**
- **失败不影响主链路**：与 `apply_rule_actions`、自动回复同样的 try/except 防御

## 3. @提及解析（需新实现）

- **语法**：`@username`，用户名精确匹配、**不区分大小写**。不匹配显示名（避免重名歧义）。
- **解析时机**：在 `sanitize_html` **之后**、入库之前，基于**纯文本** body 解析。
- **权限校验（关键）**：被 @ 的人必须**本来就能看见这张工单**
  （`visible_tickets(user).filter(pk=ticket.pk).exists()`）。
  否则 `@` 会变成「给任意人推送任意工单摘要」的越权通告渠道。
- **必须处理的坑**：`a@b.com` 里的 `@` 不能被当成提及。边界规则：`@` **前面不能是字母数字**，
  后面跟合法用户名字符。**必须写测试覆盖这个用例。**
- **受众**：有 @ → 推被 @ 者 + 认领人；无 @ → 只推认领人。
- 前端高亮渲染**先不做**（避免动现有模板）；通知文案本身能表达"有人提到了你"即可。

## 4. 安全

| 项 | 措施 |
|---|---|
| ntfy topic 可被猜 | ntfy topic **默认是公开的**，谁猜到名字谁就能收。必须用**足够长的随机 topic**（每用户每设备一个），或给实例开鉴权。按「随机 topic + 可选 token」实现 |
| 推送内容泄露 | 通知**只放主题与工单号，不放正文**。推送要经过服务器（即使是自建），邮件正文是客户隐私；点击后回 App 看全文 |
| 传输 | 强制 HTTPS |
| 客户端存储 | topic / token 存 `EncryptedSharedPreferences` |
| 邮箱凭据 | 通知链路**完全不接触** `secret_encrypted` |
| 公开仓库 | 服务器地址**不硬编码**（见 `01-决策记录.md` 决策 10） |

## 5. ntfy 部署形态

- 作为新服务加进 `docker-compose.yml`（含持久化卷）
- 配置项进 `Setting.DEFAULTS`：ntfy server URL / 可选 token / 是否启用 / 聚合窗口秒数
- 系统里已有 `Setting` 的读写与审计机制，直接复用

## 6. 订阅模型（草案）

```
Subscription
  user          FK → User
  topic         CharField   # 每设备一个随机 topic
  server        CharField   # ntfy 实例地址
  device_label  CharField   # 便于用户在设置里辨认并吊销
  enabled       Bool
  dnd_start / dnd_end       # 免打扰时段（可选）
  last_seen_at  DateTime
  created_at
```

**待人工确认**：这是新增模型，项目有「新增模型需人工确认」的约定（开发文档 §10.4）。

## 7. 落地顺序建议

**后端阶段 1 完成后，先在服务器上手动 `curl` 打通 ntfy**，再写 App。
这样能把「推送不通」与「App 有问题」两类故障分开，省掉大量排查时间。
