# 01 · 决策记录

> 来源：2026-09-26 的需求讨论。以下均为**已确认**结论，除非有新信息否则不再翻案。

## 1. 需求

为 OriDesk 做一个配套的安卓客户端，**通知是硬需求**，且**手机上要能处理工单**。
使用者是内部团队，可接受直接分发 APK（不上架），网络环境全部在国内。

## 2. 已确认决策

| # | 决策项 | 结论 | 理由 |
|---|---|---|---|
| 1 | 客户端形态 | **WebView 壳 + 原生通知** | 网页已做窄屏适配（移动顶栏/底部 Tab/抽屉/卡片流），"手机上处理工单"几乎免费获得 |
| 2 | 推送通道 | **自建 ntfy**，加进 `docker-compose.yml` | 开源可自托管、不依赖 Google 服务、协议简单、与"自部署"定位一致 |
| 3 | 后端 API 范围 | **最小必要**：只做角标 + 通知相关端点 | 网页已能干活，不做投机性 REST 面 |
| 4 | 新增 Python 依赖 | **零**（不引 DRF / JWT） | 技术栈在开发文档 §8 冻结；WebView 用 session cookie，认证问题不存在 |
| 5 | 通知事件 | 新工单进我组 / 我的工单收到新来信 / 工单被改派到我组 / 内部备注（含 @） | — |
| 6 | 受众规则 | **未认领 → 全组广播；已认领 → 只推认领人** | 与开发文档 §2.6「认领后只有认领人看到待回复」同一套所有权模型 |
| 7 | @提及 | **实现** `@username` 解析 | 用户明确选择 |
| 8 | APK 签名 | **固定 release keystore 存 GitHub Secrets** | debug 签名每次不同 → 每次升级必须卸载重装，本地数据与 ntfy 订阅丢失 |
| 9 | 后端 CD | **打 tag 自动构建镜像，部署手动触发** | 这是收发真实客户邮件的系统，push 即部署会在无人值守时打断 IMAP 收信流水线 |
| 10 | 服务器地址 | **运行时由用户填写并记住，不硬编码** | 仓库公开，硬编码会暴露内部域名；换域名也不用重新发版 |
| 11 | 构建 / CI | **GitHub Actions**（公开仓库免费额度） | 本机无 Android 工具链，云端构建是唯一能验证编译的途径 |
| 12 | 包名 / 应用名 / minSdk | `com.xinjiyuan.oridesk` / OriDesk / 26 | 默认值，用户未反对 |
| 13 | 推送接收方 | **App 内自己实现 ntfy 订阅**（"方案 B"），自己弹通知、自己管角标 | 官方 ntfy App 发的通知只会给**它自己的**图标加角标，拿不到我们要的角标（决策 3 硬需求）。详见 `移动端API约定.md` §4.2 |

## 3. 被否决 / 降级的方案

| 方案 | 处置 | 原因 |
|---|---|---|
| PWA + Web Push (VAPID) | **否决** | Chrome 的 Web Push 底层走 FCM，国内无 GMS 直接失效；国产浏览器支持参差 |
| FCM | **否决** | 国内基本不可达 |
| 厂商推送 SDK（小米/华为/OPPO/vivo/荣耀） | **后置** | 送达率最高，但要接 5 个 SDK + 5 个开发者账号，维护成本不对等 |
| 自建 WebSocket + 前台服务 | **2026-09-26 修正**：前台服务**重新用作离线通道**（承载 ntfy 订阅），见 §4③ | 原理由：耗电、被国产 ROM 杀后台。该理由未消失，但已证明绕不开 |
| DRF / JWT | **否决** | 冻结技术栈 + 零新增依赖 |
| 完整 `/api/v1/`（收件箱/详情/回复/…） | **降级** | WebView 已复用网页，当前用不上；等真要做原生 UI 时再长 |
| Flutter / KMP 跨平台 | 否决 | 只在确定要做 iOS 时才划算；本轮无 iOS 需求 |
| "工单被改派给我"事件 | **修正为"改派到我所在的组"** | 见 §4① |
| 待回复超时推送 | 不做 | 用户未勾选 |
| 管理后台（用户/组/邮箱/路由/审计）上手机 | P2，且只读为主 | 桌面场景，硬塞进手机两头不讨好 |

## 4. 讨论中被修正的三处前提

写方案时发现选项里的前提与代码/事实不符，已修正：

**① 「工单被改派给我」这个事件不存在。**
`apps/routing/services.py::reassign_ticket(ticket, group, user, reason)` 改的是 `ticket.group`
——**改派是组级的，不是用户级的**（视图提示原文「已改派到「X」，原组不再可见」）。
系统里没有"指派给某个人"的动作，只有 `claim`（自己认领）。
→ 该事件改为 **「工单被改派到我所在的组」**，受众为新组全体成员。

**② 「@我」功能不存在。**
`apps/tickets/services.py::add_note()` 只写一条 `type="note"` 的 `Message`，`body_text` 原文入库，
**没有任何 @ 提及解析**。→ 需要新实现（见 `03-通知与推送设计.md` §3）。

**③ 「通知是硬需求」与「不需要前台服务」不能同时成立——已翻案，选方案 B。**

阶段 0 写契约时发现，§3 否决「自建 WebSocket + 前台服务」的假设不成立：

- **天花板绕不开。** 国内无 GMS 下，任何推送方案都靠常驻后台进程；唯一真正改变天花的
  厂商推送 SDK 已被本表后置。所以"不用前台服务"不是可选项，只是把代价藏起来。
- **否决时的替代方案 A（装官方 ntfy App）拿不到角标。** Android 角标按 App 图标归属，
  通知由 ntfy App 发出，角标就只长在 ntfy 的图标上 —— 与决策 3「要角标」直接冲突。
- **A 也不比 B 更可靠。** 官方 ntfy App 的"即时投递"同样是前台服务 + WebSocket，照样被 ROM 杀。
- **ntfy 比当初被否决的"自建 WebSocket"多了两样实质东西**：服务端不必自建（决策 4 冻结
  零新增依赖，自建需 ASGI + Channels）；以及**消息缓存 + `since=` 断线补齐**（默认缓存 12h）。
  在"进程被杀是常态"的环境里，"能补齐"比"够实时"重要。

→ 决策 13：**方案 B**。前台服务重新用作离线通道。代价（耗电、需引导加电池白名单、
国产 ROM 延迟不可控）**明确接受**，不是没考虑到。完整论证见
[`移动端API约定.md`](移动端API约定.md) §4.2。
